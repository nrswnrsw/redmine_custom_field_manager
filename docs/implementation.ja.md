## 対応基準

2026-10-20 時点で公式の保守対象である Redmine 7.0.2、6.1.5、6.0.11 のソースコードを比較して実装する。いずれの系列も、`CustomField` の位置を STI サブクラス（フィールド種別）単位で、`CustomFieldEnumeration` の位置をカスタムフィールド単位で管理している。

## 画面の置換

Redmine のプラグインローダーが、プラグインの `app/views` を View 検索パスの先頭へ追加する標準の仕組みを利用する。Redmine 本体のファイルは変更しない。カスタムフィールドの作成、編集、コピー、削除への既存のリンクは維持する。

## 保存と競合制御

- 画面上の編集はブラウザ内に保持し、明示的な保存まで DB を更新しない。
- 保存要求には、編集開始時の全体スナップショットの SHA-256 ダイジェストを含める。
- 保存時は、対象スコープのリビジョン行、続いて対象レコードをロックし、ダイジェストを再計算する。
- Redmine 標準の保存経路にも、Rails のモデルコールバックで同じ順序のリビジョンロックを適用する。
- `CustomValue` は、選択肢の使用状況が変わり得る作成、値の変更、カスタムフィールドの変更、削除のときだけ対象のリビジョンをロックする。保存直前には参照先の選択肢が存在することをロック下で再検証し、選択肢の削除と参照の作成が競合しても孤立した参照を作らない。
- ダイジェストが異なる場合は書き込まず、HTTP 409 とサーバーの現在値を返す。
- 競合画面には、編集開始時の状態、自分の編集、サーバーの現在値の差分を表示する。サーバー側の変更と自分の変更が衝突しない場合だけ3-way統合案を返し、管理者が確定するまでは保存しない。
- 統合／強制上書きは、管理者が確認したサーバーのダイジェストを添えて再送し、確定直前に同じロック内で再照合する。対象が再び変更されていれば、もう一度409を返す。
- 並び順と履歴は同じ DB トランザクションで確定する。

カスタムフィールドの並び順、競合ロック、ダイジェストはフィールド種別単位で扱う。ある種別タブ内での保存で、別の種別の位置番号を更新することはない。

## 履歴

履歴には、対象スコープ、操作、操作者、変更前後のダイジェスト、可逆な差分を保持する。対象全体のスナップショットは、初回と20世代ごとに保存する。履歴一覧では大きなJSON列をSELECTせず、詳細表示と復元のときだけ読み込む。

選択した履歴、または指定日時より前の履歴を削除するときは、同じトランザクション内で、削除区間の直後に残る最初の履歴だけを自己完結したスナップショットに変換する。保存期間／最大世代数による自動整理も同じ処理を使う。差分チェーンの境界だけを変換するため、残るすべての履歴を展開しなくても復元可能性を維持できる。

差分JSONとスナップショットJSONの列は、64 KiBを超える10,000件規模の履歴も欠損なく保存できるようにする。MySQL／MariaDBではマイグレーションで `LONGTEXT` に拡張し、PostgreSQLとSQLiteは元から大きな `TEXT` 型を使う。列を縮小すると保存済みのデータが切り捨てられるおそれがあるため、この列拡張マイグレーションは不可逆とする。

復元は常に対象全体を扱う。カスタムフィールドの並び順は、現在と履歴のID集合が一致する場合に限り、名称などは変えずに順序だけを復元する。Key/value list は、履歴にあるIDがすべて現存するときだけ、名称・有効状態・順序を復元する。現在にしかない選択肢を削除する必要がある場合は、保存直前に使用状況を再確認する。同じIDを安全に復元できない場合は、復元全体を中断する。

## CSV

- BOM付きUTF-8で、スキーマバージョンを含むCSVを出力する。選択肢が空のリストでも、出自を示すメタデータ行を出力する。
- 数式として評価され得るセルには先頭にアポストロフィを付け、専用のフラグ列により、再インポート時に元の値へ戻す。
- 同一インスタンスかつ同一フィールドからの更新では、既存のIDを維持する。存在しないIDはエラーにする。
- 別インスタンスからのCSVではIDの一致を利用せず、管理者が確認したソースIDとローカルIDの対応だけを保存・再利用する。
- CSVの解析、差分計画の作成、最終的な適用を分離する。適用時はCSVと管理者の選択内容から計画を作り直し、プレビュー時のダイジェストと編集開始時のダイジェストを再照合する。

## 大量更新

既存レコードの名称、有効状態、位置は、検証後に、値を引用符で囲んだ `CASE` 式を使って500件単位で更新する。削除もID集合単位で行い、10,000件を移動しても10,000回の個別の `UPDATE` は発行しない。更新、履歴、マッピングは同じトランザクションで確定する。

ブラウザでは、すべての名称を通常のテキストとしてDOMに保持する。仮想スクロールはブラウザ内検索の要件に反するため採用しない。性能試験の方法と実測値は [`performance.ja.md`](performance.ja.md) に記録する。

## 検証範囲

- 自動試験は、Redmine 7.0.2／6.1.5／6.0.11 と、SQLite、MySQL 8.4、MariaDB 11.4、PostgreSQL 17の組み合わせで実行する。
- MySQL／MariaDB／PostgreSQLでは、実際のトランザクションと別々のDB接続を使い、選択肢の削除と、その選択肢を使う保存済み入力値の作成が競合する場合を、両方の順序で試験する。SQLiteには行ロックがないため、この2つの試験だけをスキップする。
- Redmine 7.0.2では、Playwrightによる実ブラウザ試験で、編集、Undo/Redo、一括移動、保存、CSVプレビュー、2つのページ間の競合、安全な統合を確認する。
- DBの直接更新や、モデルコールバックを意図的に迂回する未知のプラグインによる更新に対しては、競合保護を保証しない。
